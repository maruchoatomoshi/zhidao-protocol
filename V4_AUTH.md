# ZHIDAO V4 — локальный вход и серверные роли

Актуализация 2026-09-08: вход и сопряжение MAX уже работают; кейсы используют
существующие сессии/CSRF, а права организатора проверяют в границах сезона.
В режиме оформления личные API не вызываются; после входа кейсы и коллекция
показывают серверные данные. Подробности — `V4_CASES.md`. Остальные разделы
по-прежнему могут оставаться заглушками.

V4 API не требует Telegram. Внутренний аккаунт связывается с identity provider
`local`; Telegram и будущий MAX остаются дополнительными способами входа.

## Защитные свойства

- пароли хешируются `scrypt` с индивидуальной случайной солью;
- пять неверных паролей блокируют credential на 15 минут;
- login дополнительно ограничен по IP, по умолчанию 120 попыток в минуту;
- в SQLite сохраняются только SHA-256-хеши session/CSRF-токенов;
- session cookie — `HttpOnly`, `Secure` по умолчанию и `SameSite=Lax`;
- изменения требуют совпадающих CSRF cookie и `X-CSRF-Token`;
- роли загружаются из БД на каждом запросе, поэтому отзыв действует сразу;
- создание сезона разрешено только глобальному `system_admin`;
- `X-Idempotency-Key` исключает двойное создание при повторной отправке;
- входы, выходы, ошибки входа и создание сезона попадают в append-only AuditLog.

## 1. Первичный bootstrap

Команда интерактивно спрашивает пароль и не принимает его аргументом командной
строки. По умолчанию атомарно создаются первый `system_admin` и черновик
`hainan-v4`.

```powershell
New-Item -ItemType Directory -Force .codex-tmp\v4-local | Out-Null
.\.venv-travel\Scripts\python.exe -m zhidao_v4.bootstrap `
  --db .codex-tmp\v4-local\zhidao.db `
  --username architect `
  --display-name "Architect"
```

Повторный bootstrap запрещён, если глобальный системный администратор уже
существует.

## 1a. Остальные учётные записи и смена пароля

`bootstrap` создаёт только первого системного администратора и только один
раз. Всё остальное — вожатые, участники, служебная учётка бота — заводится
отдельной командой:

```bash
python -m zhidao_v4.provision --db <база> \
  --username mikhail --display-name "Михаил Юрьевич" \
  --role operator --random-password
```

Роли: `system_admin`, `architect`, `operator`, `participant`. Логин — 3–64
символа из `a-z 0-9 . - _`, приводится к нижнему регистру.

Посмотреть, кто уже заведён, — той же командой:

```bash
python -m zhidao_v4.provision --db <база> --list
```

Повторное заведение с занятым логином не перезаписывает существующую
учётку, а отказывает: пароль и роли прежней остаются нетронутыми.

Изменить роли уже заведённой учётки:

```bash
python -m zhidao_v4.roles --db <база> --username mikhail --grant system_admin
python -m zhidao_v4.roles --db <база> --username mikhail --revoke operator
```

Роли складываются: выдача новой не снимает прежнюю. Отзыв не удаляет строку,
а помечает её `revoked_at` — кто и когда имел права, остаётся в истории.
Роли перечитываются на каждом запросе, а не запекаются в сессию, поэтому и
выдача, и отзыв действуют немедленно, в том числе на уже открытые сессии
(это же проверяет `test_role_revocation_takes_effect_for_an_existing_session`).

Смена пароля существующей учётки:

```bash
python -m zhidao_v4.passwd --db <база> --username architect --random-password
```

Меняет пароль на месте: `public_id`, роли, привязанные внешние личности и
журнал остаются прежними. Заодно **отзывает все действующие сессии** этой
учётки (иначе смена пароля не прекращала бы прежний доступ — а меняют его
обычно именно ради этого) и **снимает блокировку** после неудачных попыток
входа: человек, дошедший до администратора за новым паролем, уже доказал,
кто он.

`--random-password` печатает пароль ровно один раз, в stdout; в базе с этого
момента только его scrypt-хэш. Без этого ключа пароль спрашивается
интерактивно и в историю оболочки не попадает. Аргументом командной строки
пароль не принимается ни одной из команд — он остался бы в истории и в `ps`.

Обе команды пишут в базу напрямую. Это дозволенный случай второго писателя:
одна короткая транзакция, запуск вручную, никакого ожидания сети внутри
неё. Запрет из `CLAUDE.md` касается долгоживущего второго писателя, каким
был бот сезона 1.

**Чего пока нет:** человек не может сменить себе пароль сам — только через
того, у кого есть доступ к серверу. Поле `must_change_password` в
`v4_local_credentials` существует с миграции 0002, но **нигде не читается**:
выставить его можно, а никакого поведения за ним нет. Не полагаться на него
как на защиту.

## 1b. Служебный экран в приложении

`Ещё → Админка` (`data-screen="admin"`, `zhidao_v4/static/app/admin.js`).
Плитка скрыта в разметке и показывается только тому, у кого есть роль
`operator`, `architect` или `system_admin` — глобальная или сезонная.

Это **удобство, а не контроль доступа**. Все данные экрана приходят
эндпоинтами, которые проверяют роль сами, и участник, дошедший до них
запросом, получает 403 (`tests/test_v4_admin_console.py`). Прятать кнопку
имеет смысл ровно для того, чтобы человек не упирался в отказ там, где ему
и не нужно.

Что за какой ролью:

| Раздел экрана | Эндпоинт | Нужна роль |
|---|---|---|
| Сводка и журнал | `GET /api/v4/admin/overview` | `architect`, `system_admin` (глобальная) |
| Участники, код MAX | `GET /api/v4/admin/accounts`, `POST .../link-codes` | `operator` и выше (глобальная) |
| Сезоны | `GET /api/v4/seasons` | любой вошедший |
| Попытки | ссылка на экран «Кейсы» | `can_manage` сезона (в том числе сезонная роль) |

Отсюда две особенности, которые видно на экране. Вожатому по умолчанию
открывается «Участники», а не «Сводка»: сводка ему всё равно ответит
отказом. А сезонные роли в табличке доступа помечены номером сезона —
разница между сезонной и глобальной ролью объясняет половину отказов здесь.

Выдача кода MAX аннулирует прежний код этого человека, поэтому кнопка
требует второго нажатия и говорит об этом словами. Сам код показывается
один раз: в базе с этого момента только его отпечаток.

Код показывается группами по четыре — его диктуют вслух. Набранный с
пробелом он подходит: лишние символы отбрасывает и приложение, и сервер.

Отказ на `/api/v4/auth/max` со статусом 409 несёт структурный `detail`:

| `reason` | Что случилось | Что делать |
|---|---|---|
| `link_required` | MAX опознан, аккаунт не сопоставлен | ввести код от вожатого |
| `account_already_linked` | Код верный, но у аккаунта уже есть привязка MAX | новый код не поможет — снимать прежнюю привязку |

Второй случай существует потому, что схема разрешает аккаунту ровно одну
привязку на провайдера (`UNIQUE(account_id, provider_code)`). Команды
отвязки пока нет.

## 2. Локальный запуск API

```powershell
$env:ZHIDAO_V4_DB_PATH = (Join-Path (Get-Location) '.codex-tmp\v4-local\zhidao.db')
$env:ZHIDAO_V4_COOKIE_SECURE = '0'
.\.venv-travel\Scripts\python.exe -m uvicorn zhidao_v4.api:create_app `
  --factory --host 127.0.0.1 --port 8770
```

`ZHIDAO_V4_COOKIE_SECURE=0` допустим только для локального HTTP. На тестовом и
production-сервере cookie обязана оставаться `Secure`.

Проверка: `http://127.0.0.1:8770/api/v4/health`.

Админка Архитектора: `http://127.0.0.1:8770/architect/`.

Статический дизайн-превью личного приложения:
`http://127.0.0.1:8770/app/`. Он доступен без входа только для согласования
визуального направления и пока не содержит аккаунтов, персональных данных или
подключений к игровым API.

После входа доступны:

- обзор состояния V4 и текущего Hainan draft;
- последние записи AuditLog;
- редактирование названия, дат, часового пояса и темы Hainan;
- системная диагностика и версия схемы;
- адаптивный интерфейс для desktop и телефона.

Форма сезона использует optimistic locking. Если та же конфигурация была
изменена в другой вкладке, устаревшая форма не перезапишет новые данные и
получит конфликт версии.

## 3. Контракт входа

```text
POST /api/v4/auth/login
GET  /api/v4/auth/me
POST /api/v4/auth/logout
GET  /api/v4/seasons
POST /api/v4/seasons
PATCH /api/v4/seasons/{season_id}
GET  /api/v4/admin/overview
```

Для мутаций клиент передаёт session cookie, CSRF cookie,
`X-CSRF-Token` и уникальный `X-Idempotency-Key`. Пароль и токены не должны
попадать в URL, логи или localStorage.

Сейчас bootstrap создаёт только системного администратора. Массовая выдача
детских аккаунтов будет отдельным операторским сценарием после решения о
первичных логинах и восстановлении доступа.
