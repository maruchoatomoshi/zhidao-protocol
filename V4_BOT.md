# Бот ZHIDAO в MAX

Что это, как устроено, как поднять и что в нём намеренно ещё не сделано.

Последнее обновление: 2026-09-08.

Смежные документы: `V4_AUTH.md` (вход и роли), `V4_DECISIONS.md` (что решено
и не пересматривается), `CLAUDE.md` (правила по SQLite — они здесь ключевые).

## Главное правило: бот не открывает базу

Бот — отдельный процесс, который **ходит в API V4 по HTTP** под служебной
учётной записью. Он не подключается к `zhidao.db` ни на чтение, ни на
запись.

Это не вкусовое решение. 2026-06-09 в сезоне 1 бот был вторым писателем в ту
же SQLite и держал write-lock, пока внутри транзакции ждал ответа от
мессенджера. Каждый пишущий эндпоинт API вставал на 27–1463 секунды.
Единственный писатель — API; всё остальное разговаривает с ним по HTTP.

Побочная выгода: действия бота проходят те же проверки ролей и ложатся в тот
же `v4_audit_log`, что и действия человека в консоли Архитектора. На вопрос
«кто выдал этот код сопряжения» есть ответ.

## Состав

```
zhidao_v4/bot/
  max_api.py    клиент Bot API MAX (httpx, длинный опрос)
  backend.py    клиент API V4: логин служебной учёткой, сессия, CSRF
  commands.py   разбор событий MAX и словарь команд
  __main__.py   точка входа: --check, --set-commands, --dump-updates, цикл
```

Библиотеки для MAX нет и не нужно: весь протокол — четыре запроса с JSON, а
`httpx` уже в `requirements-web.txt`.

Формы запросов и объектов сверены со схемой официального клиента MAX
(`github.com/max-messenger/max-bot-api-client-go`, ветка `v2`, файлы
`schema.yaml` и `const.go`, прочитано 2026-09-07):

- база `https://platform-api2.max.ru`; `platform-api.max.ru` помечен там как
  «Deprecated: not allowed»;
- токен — заголовком `Authorization: <токен>`, голым, без `Bearer`; передача
  токена в строке запроса больше не поддерживается;
- у входящего сообщения текст лежит в `message.body.text`, отправитель — в
  `message.sender.user_id`, адресат — в `message.recipient`.

Если MAX что-то поменяет, сверяться не с памятью, а с реальностью:
`python -m zhidao_v4.bot --dump-updates` печатает сырой JSON событий и ничего
не отвечает.

## Команды

Работают сейчас:

| Команда | Кому | Что делает |
|---|---|---|
| `/start` | всем | Приветствие и кнопка запуска мини-приложения |
| `/app`, `/приложение` | всем | Кнопка запуска мини-приложения |
| `/help`, `/помощь` | всем | Список команд; вожатому — расширенный |
| `/myid`, `/мойid` | всем | Идентификатор MAX (нужен, если вход сломался) |
| `/кто <имя>` | вожатому | Поиск по ростеру: номер, имя, привязан ли MAX |
| `/код <имя или номер>` | вожатому | Выдать код сопряжения на 30 минут |
| `/статус` | вожатому | Состояние сервера и версия схемы |

Команды пекинского сезона (`/баллы`, `/рейтинг`, `/перекличка`, `/подъем`,
`/award`, `/penalize`, `/зп`, `/подарить`, `/broadcast`, `/погода`, `/bug`,
`/вопрос`, `/напоминания`) **перечислены в коде и отвечают тем, чего именно
не хватает**, а не «неизвестная команда». Их нельзя включить, пока в V4 нет
самих систем: экономики, переклички, наград, рассылки. Список лежит в
`PENDING_COMMANDS` (`zhidao_v4/bot/commands.py`) — когда система появится,
команда переезжает оттуда в обработчики.

## Кто считается вожатым

Список идентификаторов MAX в переменной `ZHIDAO_V4_BOT_OPERATORS`, а не роль
из базы. Причина — замкнутый круг: чтобы прочитать роль из базы, MAX-аккаунт
вожатого должен быть уже привязан, а привязка требует кода сопряжения,
который выдаёт вожатый. Список в окружении этот круг размыкает. Операторов
пять-шесть, цена невелика. Когда первый вожатый привязан, список можно будет
заменить проверкой роли — но не раньше.

Свой идентификатор человек узнаёт командой `/myid`.

## Развёртывание на тестовом сервере

Про сам сервер (`china.marucho.icu`, что там ещё живёт и чего не трогать) —
см. `CLAUDE.md` и заметку о тестовом сервере. Ниже только про бота.

### 1. Служебная учётка с ролью оператора

```bash
sudo -u www-data bash -c 'cd /opt/zhidao-v4 && ./.venv/bin/python -m zhidao_v4.provision \
  --db /var/lib/zhidao-v4/zhidao.db \
  --username bot.max --display-name "Бот MAX" \
  --role operator --random-password'
```

`cd` здесь обязателен: `python -m` ищет пакет относительно текущего
каталога, а из домашнего каталога `zhidao_v4` не виден. Юнит systemd
обходится без него только потому, что у него есть `WorkingDirectory`.

Пароль печатается **один раз** — в базе с этого момента только его
scrypt-хэш. Сразу перенести его в файл окружения, в историю оболочки он не
попадает.

### 2. Переменные окружения

Токен бота уже лежит в `/etc/zhidao-v4/v4.env` как `ZHIDAO_V4_MAX_BOT_TOKEN`
— он нужен и API (для проверки подписи запуска мини-аппа), и боту. Дописать
туда же:

```ini
ZHIDAO_V4_API_URL=http://127.0.0.1:8770
ZHIDAO_V4_BOT_USERNAME=bot.max
ZHIDAO_V4_BOT_PASSWORD=<пароль из шага 1>
ZHIDAO_V4_BOT_OPERATORS=<id вожатых через запятую>
ZHIDAO_V4_BOT_WEBAPP=<публичное имя бота в MAX>
ZHIDAO_V4_APP_URL=https://china.marucho.icu:8443/app/
```

`ZHIDAO_V4_BOT_WEBAPP` — публичное имя бота (то, что после `@`). Без него
кнопка мини-аппа не рисуется: поле `web_app` в схеме MAX обязательное, и
запрос с пустым значением отвалится. Пока имя не прописано, `/app` отвечает
ссылкой из `ZHIDAO_V4_APP_URL`.

Файл читается и юнитом API, и юнитом бота, права на него — как были
(`0600`, владелец `www-data`).

### 3. Проверка до запуска

```bash
sudo bash -c 'cd /opt/zhidao-v4 && set -a; . /etc/zhidao-v4/v4.env; set +a; ./.venv/bin/python -m zhidao_v4.bot --check'
```

Выводит, кто бот по мнению MAX, отвечает ли API, под какой учёткой и с
какими ролями бот вошёл. Возвращает 1, если что-то не так — в том числе если
у учётки нет роли оператора и коды сопряжения выдать не выйдет.

От root, а не от `www-data`: `v4.env` доступен на чтение только root'у
(systemd читает его до сброса привилегий), а `--check` и `--set-commands`
только ходят по HTTP и ничего не пишут, так что root-овских файлов после
себя не оставляют. Учётку из шага 1 заводить надо, наоборот, именно от
`www-data` — она пишет в базу, и файлы WAL рядом с ней не должны стать
root-овскими.

### 4. Меню команд в MAX

```bash
sudo bash -c 'cd /opt/zhidao-v4 && set -a; . /etc/zhidao-v4/v4.env; set +a; ./.venv/bin/python -m zhidao_v4.bot --set-commands'
```

Разово, и повторять после изменения `MENU_COMMANDS`.

### 5. Юнит systemd

`/etc/systemd/system/zhidao-v4-bot.service`:

```ini
[Unit]
Description=ZHIDAO V4 MAX bot
After=network-online.target zhidao-v4.service
Wants=network-online.target

[Service]
Type=simple
User=www-data
Group=www-data
WorkingDirectory=/opt/zhidao-v4
EnvironmentFile=/etc/zhidao-v4/v4.env
ExecStart=/opt/zhidao-v4/.venv/bin/python -m zhidao_v4.bot
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ProtectHome=true
UMask=0077

[Install]
WantedBy=multi-user.target
```

Здесь **нет** `ReadWritePaths=/var/lib/zhidao-v4` — и это не упущение. Боту
не нужен доступ к каталогу базы, и не давать его — самый простой способ
гарантировать, что правило «бот не открывает базу» не нарушится по
случайности.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now zhidao-v4-bot
sudo journalctl -u zhidao-v4-bot -f
```

### 6. Адрес мини-приложения

В настройках бота в MAX указать `https://china.marucho.icu:8443/app/`.
Заголовки на `/app/` уже разрешают встраивание с доменов MAX
(`frame-ancestors 'self' https://max.ru https://*.max.ru`), а консоль
Архитектора остаётся полностью незакладываемой в рамку.

## Что проверено и чем

`tests/test_v4_bot.py`:

- разбор событий MAX в той форме, что описана в его схеме, включая
  `bot_started` как эквивалент `/start` и отбрасывание сообщений от ботов;
- разбор команды с дописанным именем бота (`/код@zhidao_bot Иванов`);
- команды поверх **настоящего** API V4 — фальшивый только мессенджер, так
  что `/код` реально проходит проверку роли, CSRF и журнал;
- участник не может выдать код;
- при неоднозначном имени код не выдаётся, а запрашивается уточнение;
- в групповом чате бот молчит на обычный текст и отвечает в чат, а не в
  личку;
- токен уходит заголовком и не попадает в строку запроса;
- `marker` при первом опросе опускается, а не шлётся как `null`.

`tests/test_v4_auth_api.py` дополнительно проверяет, что ростер и коды
закрыты от участника на уровне сервера.

Чего тесты **не** доказывают: что MAX действительно отвечает так, как
описано в его схеме. Живого прогона против Bot API MAX ещё не было — токен
лежит только на сервере. Первый запуск `--check` на сервере и есть эта
проверка.

## Открытые вопросы

- Список вожатых в окружении вместо роли из базы (см. выше).
- Длинный опрос вместо вебхука. Документация MAX называет опрос «только для
  разработки», но вебхук требует публично доступного HTTPS-эндпоинта, а у
  нас TLS на нестандартном порту 8443 и сертификат без автопродления.
  Переезжать на вебхук — после того, как с TLS станет спокойнее.
- Рассылка (`/broadcast`) потребует хранить `chat_id` диалога с каждым
  участником: `provider_subject` в `v4_external_identities` — это
  идентификатор пользователя MAX, а не чата. Отдельная задача.
